# UI review — 2026-09-17

Scope: `src/ui/*.tsx`, `src/ui/*.ts` (non-test), `src/cli.tsx`. Ink/React correctness review
(stale closures, missing deps, key bugs, leaks, width/height math, off-by-ones, races).

## Findings

### 1. `src/ui/App.tsx:676-685` — race condition + unguarded non-null assertion can crash the TUI in split view

```js
const waitingNotice =
  actionSessionId &&
  (view === "split" ? readTaskState(actionSessionId)?.activity : taskState?.activity) &&
  isWaitingForUser(
    view === "split" ? readTaskState(actionSessionId)?.activity : taskState?.activity,
  )
    ? waitingBannerMessage(
        (view === "split" ? readTaskState(actionSessionId)?.activity : taskState?.activity)!.toolName,
      )
    : undefined;
```

`readTaskState()` (`src/store.ts`) does a synchronous `readFileSync` + `JSON.parse` straight off disk;
it is *not* backed by React state, so nothing guarantees the three separate calls in this expression
see the same file content. The state files are written by an external hook process at any time
(write-then-rename), so between the first call (used for the truthiness/`isWaitingForUser` checks)
and the third call (whose result is force-unwrapped with `!`), the file can legitimately change —
e.g. `activity` can be cleared/replaced or the session file can even be deleted (the `d` key deletes
sessions). If the third read no longer has `.activity`, `(...)!.toolName` throws
`Cannot read properties of undefined`, crashing the whole Ink render (this branch is only reachable in
`view === "split"`, i.e. right after entering split mode with `v`).

This is the only `)!.` non-null assertion in the file (verified via grep) and the only spot that
re-derives the same value from a mutable external source three times in one expression instead of
reading it once.

**Why it's a bug:** unhandled exception path triggered by an ordinary, expected race (concurrent file
writes from the hook while split view is open), not a hypothetical edge case.

**Suggested fix:** read once per render and reuse:
```js
const actionActivity =
  view === "split" ? readTaskState(actionSessionId)?.activity : taskState?.activity;
const waitingNotice =
  actionSessionId && actionActivity && isWaitingForUser(actionActivity)
    ? waitingBannerMessage(actionActivity.toolName)
    : undefined;
```

Severity: **High** (crash), but requires split view + concurrent hook writes to trigger.

### 2. `src/ui/TaskList.tsx:131-133` — off-by-one in `subagentRows`, undercounts the sub-task block's own `marginBottom`

```js
const subagentRows = subagents && subagents.dispatches.length > 0
  ? 1 + subagents.dispatches.length + (subagents.latestSidechainActivity ? 1 : 0)
  : 0;
```

This is fed into `snapshotExtraRows` → `pageSize = pageSizeFromTerminal(termRows, LIST_CHROME_ROWS + snapshotExtraRows)`,
i.e. it's the "how many terminal rows does this block actually occupy" budget used to size the
scrollable task list so the whole screen fits without overflowing.

`SubagentsBlock` (same file, lines 78-93) renders:
```jsx
<Box marginBottom={1} flexDirection="column">
  <Text dimColor>Sub-task（Agent 派發）</Text>       {/* 1 row */}
  {subagents.dispatches.map(...)}                    {/* dispatches.length rows */}
  {subagents.latestSidechainActivity ? <Text.../> : null}  {/* 0/1 row */}
</Box>                                                {/* + 1 blank row from marginBottom */}
```
i.e. 1 + dispatches.length + (sidechain?1:0) + **1** (margin) rows are actually drawn, but the
`subagentRows` formula omits the final `+ 1` for the block's `marginBottom={1}`.

Contrast with the `contextSnapshot` block just above it, which *does* budget for its own
`marginBottom={1}`:
```js
(contextSnapshot ? 2 + (contextSnapshot.breakdownLine ? 1 : 0) + (contextSnapshot.gauge ? 1 : 0) : 0)
```
(the base `2` = occupiedLine + margin row). The subagents block should follow the same pattern.

**Why it's a bug:** `pageSize` ends up one row larger than what actually fits whenever any Agent
sub-task dispatch is shown (this is the feature added in `4c4092c feat: track Agent sub-task agent
dispatches in watch TUI`), so the computed page of visible task rows plus the footer hint line can
overflow the terminal by one line / get clipped by the terminal scrollback, and the
`↑ 還有 N 行` / `↓ 還有 N 行` counters will be off by one row relative to what's actually on screen.

**Suggested fix:**
```js
const subagentRows = subagents && subagents.dispatches.length > 0
  ? 2 + subagents.dispatches.length + (subagents.latestSidechainActivity ? 1 : 0)
  : 0;
```

Severity: **Low/Medium** (cosmetic layout overflow, not a crash or data bug).

### 3. `src/ui/AdvicePanel.tsx:79-83` — `detailLines` list keyed by raw text, can collide

```jsx
{row.detailLines?.map((line) => (
  <Text key={line} dimColor>
    {"  "}· {line}
  </Text>
))}
```

Unlike every other list in this codebase (which key by id, or by `index`/`start+index` combined with
content), this one keys purely by the line's own text with no index fallback. If a single advice
item's `detailLines` ever contains two identical strings (e.g. two lines both reporting the same
rounded token count), React will see a duplicate key within that map, which can cause it to reuse/skip
a DOM node incorrectly on updates (classic duplicate-key list bug).

**Suggested fix:** `key={`${index}-${line}`}` using the map's index.

Severity: **Low** (requires duplicate detail-line text to manifest; no evidence yet that `detailLines`
producers emit duplicates, but nothing guarantees they won't).

## Not flagged (considered and ruled out)

- Ink's `useInput` re-subscribes its internal listener every render (dependency array includes the
  handler itself — see `node_modules/ink/build/hooks/use-input.js`), so inline callbacks in
  `App.tsx`/`TaskList.tsx`/etc. that close over component state are **not** stale-closure bugs; a
  fresh closure is attached before the next keypress can be processed.
- The advice-watcher `useEffect` in `App.tsx:483-540` has no `return` cleanup, but this is intentional
  (watchers are persisted in a ref across re-runs and only closed when a session disappears or on
  unmount via the dedicated effect at `App.tsx:542-547`) — not a leak.
- All interval timers (`App.tsx:663-668`, `670-674`) and directory/file watchers
  (`App.tsx:448-479`, `564-579`, `581-598`) have matching cleanup.
- `src/ui/scroll-window.ts` matches its paired test file (`scroll-window.test.ts`) exactly.
